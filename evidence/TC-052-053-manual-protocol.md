# TC-052 / TC-053 真实浏览器人工验收协议

状态：`manual-execution-required`。协议版本：`1.0`。

本文只定义最终发布包的人工验收步骤，不包含、推断或代签任何执行结果。空白模板、源代码检查、DOM 快照、自动化脚本、AI 代理和无障碍扫描均不得被解释为 TC-052 或 TC-053 已通过。

## 1. 范围与正式依据

- TC-052 验证键盘核心流程：`1`—`9` 选择当前列表项、`Enter` 确认、`Esc` 返回、`/` 搜索、`G` 打开今日、`L` 打开日志、高风险二次确认、普通浏览不抢占输入焦点，以及所有鼠标操作都有键盘等价路径。
- TC-053 验证纯文字表现和可访问性：不依赖图像、动画、声音或颜色传达必要信息；显示设置可用；紧凑视图满足规定信息密度；日志和表格能被屏幕阅读器按语义顺序读取。
- 本协议的通过只适用于实际测试的发布包和浏览器/辅助技术组合，不能外推到未测试的构建或平台。

## 2. 发布包冻结与哈希绑定

测试前必须先生成并冻结 `evidence/release-manifest.json`。若该文件不存在、无法解析或任何校验失败，停止测试并把结果记为 `BLOCKED`，不得继续签署。

执行者须在结果报告中原样记录以下字段：

- 本协议文件最终字节的 SHA-256（`protocol_sha256`）；
- `format`，必须为 `farm-journal-release-manifest-v1`；
- `generated_at`；
- `bundle_hash`；
- `files.length`；
- `files[]` 中 `dist/index.html` 对应的相对路径项（清单内通常为 `index.html`）及其 `bytes`、`sha256`；
- `files[]` 中 `src/presentation/app.js` 与 `src/presentation/styles.css` 的 `bytes`、`sha256`。

开始浏览器操作前须独立核对：

1. `files[]` 中每个路径都存在于本次提供的 `dist/`，字节数和 SHA-256 一致。
2. `bundle_hash` 是清单 `files` 数组按项目规范进行规范化序列化后的 SHA-256。
3. `evidence/acceptance-summary.json` 的 `release_bundle.manifest` 指向 `release-manifest.json`，其中 `files` 和 `bundle_hash` 与清单一致。
4. 浏览器实际打开的是该 `dist/`，不是仓库根目录、旧服务、缓存副本或开发服务器的另一份构建。
5. 测试开始后不再重新构建或改动 `dist/`。

TC-052 与 TC-053 可以在同一冻结发布包上连续执行，但每一项都必须独立给出结论。

## 3. 环境与测试数据

### 3.1 通用环境

- 通过本机 HTTP 静态服务器打开最终 `dist/index.html`，不直接使用 `file://`。
- 记录操作系统、浏览器名称和完整版本、语言、视口 CSS 像素、浏览器缩放、屏幕缩放、键盘布局、时区与刷新点。
- 基准视觉环境为不小于 `1366 × 768` CSS 像素、浏览器缩放 100%。若实际支持范围另有约定，同时记录该范围。
- 关闭会改变网页快捷键、焦点或朗读结果的非辅助性扩展。
- 测试者不得使用鼠标、触控板或触屏完成标为“键盘”的步骤。
- 屏幕录像、语音录像或逐字朗读记录须事先取得真人测试者同意。

### 3.2 两类浏览器配置

准备两个互不污染的配置：

1. **干净配置**：清空本应用的 Local Storage，从建档时区和刷新点确认页开始，用于建档、首次播种、工作调整和基础焦点流程。
2. **可丢弃的已发展配置**：必须由同一最终发布包通过正常 UI、正常日结或有来源记录的导入流程产生；包含至少一种可出售产品、一个可选择事件，以及一个可触发的高风险操作。不得直接改 Local Storage、调用内部命令或注入完成状态。

若通过导入获得已发展配置，须记录导入文件 SHA-256、来源、生成步骤和导入前后的校验结果。该配置只用于覆盖条件性 UI，不替代干净配置流程。

## 4. 记录值与失败处理

每一步只允许以下结果值：

- `PASS`：真人在规定环境中完成，实际结果与期望完全一致；
- `FAIL`：已执行但结果不符，必须关联缺陷编号和证据；
- `BLOCKED`：环境、发布包或数据前置条件阻止执行，必须记录原因；
- `NOT RUN`：尚未执行。

`BLOCKED`、`NOT RUN`、空白、`N/A` 或“源代码看起来正确”均不算通过。执行中发现失败后可以继续收集其他项证据，但最终结论仍为 `FAIL`；修复后必须生成新的 `release-manifest.json` 和 `bundle_hash`，并在新发布包上重新完整执行受影响项。

## 5. TC-052 键盘核心流程

### 5.1 数字键与确认的验收语义

为避免把数字键本身变成误操作，本协议固定以下解释：

- 当前页最多九个明确编号的可见列表项或主要操作分别对应 `1`—`9`。
- 隐藏字段、文本/数字输入框、下拉框、禁用项和搜索后隐藏的项不得占用编号。
- 按数字键只选择或聚焦目标，不得提交表单、改变资源或执行命令。
- 所选目标必须具有可见编号，并向辅助技术暴露等价快捷键信息。
- 按 `Enter` 才执行已选择的普通操作；一次按键只能产生一次命令。
- 搜索过滤或页面重绘后，编号必须与当前可见项目一致，不能指向已消失的节点。
- 文本、数字或下拉输入期间，字母和数字快捷键不得抢走输入焦点或触发游戏操作。
- 高风险对话框打开后，页面级快捷键暂停；默认安全焦点可以停在“取消”。测试者必须显式移动到“确认执行”并按 `Enter` 才能提交。

### 5.2 必执行步骤

| ID | 真人键盘步骤 | 期望结果 |
|---|---|---|
| K-01 | 从地址栏载入干净配置；只用 Tab 找到“跳到主要内容”并按 Enter | 焦点进入主内容；焦点指示清晰；没有键盘陷阱 |
| K-02 | 用 Tab、Shift+Tab、方向键和 Enter 完成时区、刷新点建档 | 字段可达、标签清楚、校验错误可读；只创建一个存档并进入今日 |
| K-03 | 从头到尾遍历十个主导航按钮，再反向遍历 | 顺序与视觉/DOM 顺序一致；当前页状态可感知；焦点始终可见 |
| K-04 | 在至少两个含多个项目的页面依次按 `1`—`9` | 每个有效数字只聚焦/选择对应的可见编号项；无命令、资源或存档副作用 |
| K-05 | 在 K-04 已选择的普通目标上按 Enter | 只执行一次预期操作；结果保存；成功或失败消息可感知 |
| K-06 | 在任务名称、数量、WP、专注、标题和搜索字段中输入 `1`、`9`、`g`、`l`、`/` | 字符进入字段或按该控件的原生语义工作；页面不跳转且焦点不丢失 |
| K-07 | 从非编辑状态分别按 `G`、`g`、`L`、`l` | G/g 打开今日，L/l 打开日志；主内容焦点和当前导航状态同步更新 |
| K-08 | 从非编辑状态按 `/`，输入一个有结果和一个无结果的查询；在搜索仍有焦点时按 Esc | `/` 聚焦搜索；过滤只影响当前页；Esc 清空查询、返回今日并把焦点置于主内容，且不提交任何游戏操作 |
| K-09 | 从今日以外页面按 Esc；在确认对话框中按 Esc | 普通页面返回今日；对话框取消且不执行高风险操作，焦点返回合理位置 |
| K-10 | 在田区页用键盘选择作物并播种，再完成一次条件灌溉 | 原生选择控件和按钮均可操作；状态、工时和存档结果正确且只变化一次 |
| K-11 | 在今日页新增或修改工作，检查 WP/专注字段并确认日程 | 完整流程无需鼠标；输入焦点不被快捷键抢占；确认后状态正确 |
| K-12 | 在已发展配置中查看实际价格、把一件产品放入出售箱并查看到账预览 | 表格、按钮和页面导航均有键盘路径；价格及出售箱状态可读 |
| K-13 | 展开事件正文，选择一个事件选项，查看效果预览，再确认 | `details/summary`、选项、预览和确认全程可键盘操作；事件只提交一次 |
| K-14 | 触发动物转让、取消工程或创建新存档等高风险操作；先取消一次，再在可丢弃配置中确认一次 | 对话框确实阻止后台操作；取消无副作用；明确确认后才执行；模态期间全局快捷键不改变后台页 |
| K-15 | 用键盘导出备份，再通过文件选择器导入一份有效备份 | 网页控件和操作系统文件选择器均可键盘完成；导入/导出结果可读且存档有效 |
| K-16 | 覆盖按钮、链接、输入框、选择框、复选框、文件选择、summary 和对话框，逐项对照鼠标操作清单 | 每种鼠标操作都有 Tab/方向键/Space/Enter 或已记录快捷键的等价路径 |
| K-17 | 在命令完成、校验失败、搜索、页面重绘和对话框关闭后继续操作 | 焦点不会无提示落到页面开头或不可见节点；没有重复提交或键盘陷阱 |

### 5.3 TC-052 通过条件

- K-01—K-17 全部为 `PASS`；
- 数字键符合 5.1 的“选择后 Enter 确认”语义；
- 所有可见鼠标操作完成键盘等价路径盘点；

## 7. 证据要求

每个 `PASS` 至少包含：执行者、时间、环境、实际结果摘要和可追溯证据引用。可接受证据包括经同意的录屏时间码、屏幕阅读器字幕/语音摘要、截图、导出存档哈希、浏览器控制台记录和缺陷单；单独的截图不足以证明键盘顺序或实际朗读。

发现问题时记录：步骤 ID、复现率、期望、实际、焦点位置、实际朗读摘要、严重度、浏览器/辅助技术版本、`bundle_hash` 和证据引用。修复后的复测必须使用新发布包清单并重新判断签署是否失效。

## 8. 签署角色与结论

结果报告必须至少包含以下真实签署：

- TC-052 键盘执行者：确认全程键盘执行和实际结果；
- TC-053 辅助技术执行者：确认本人实际使用并听取指定屏幕阅读器；
- QA：审核步骤完整性、缺陷状态、证据链和发布包绑定；
- 最终批准者（game designer 或被正式授权的产品负责人）：确认验收语义和发布结论。

每个签署包含姓名、角色、日期时间、协议版本、`bundle_hash`、`PASS` 或 `FAIL` 以及签署声明。电子签署必须可归属到具体真人。AI、自动化账号、空白姓名、模板文字和“代表某角色”的推断均无效。

TC-052 与 TC-053 必须分别给出 `PASS` 或 `FAIL`。只有所有必执行项均为 `PASS` 且签署齐全时，才可把相应 TC 从待验收改为通过。

## 9. 签署失效规则

出现以下任一情况，相关 `PASS` 立即失效并恢复为待验收：

- `release-manifest.json` 缺失、损坏或无法复算；
- `bundle_hash` 改变；
- `files[]` 的路径、字节数或任一 SHA-256 改变；
- 浏览器实际加载的文件与清单不一致或命中旧缓存；
- 协议发生会改变步骤、门槛或通过语义的修订；
- 结果报告记录的 `protocol_sha256` 与实际执行协议不一致；
